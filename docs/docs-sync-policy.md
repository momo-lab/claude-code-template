# ドキュメントと実ファイルの同期ルール

**読むタイミング**: 常に意識する。特に`docs/`配下または対応する実ファイル
（設定・スキーマ・テストコード）を変更する時は必ず確認する。

## 原則

`docs/`配下の記述には、性質の異なる2つの状態がありうる。これを区別せずに
「docsと実ファイルは常に一致していなければならない」と扱うと、大きな機能を
設計してdocsに反映した直後のような、正当な状態まで「ズレ」として扱ってしまう。

- **実装済みの内容**: 実ファイル（コード・設定・migrations）の記述と完全に一致
  していなければならない。ここが食い違っている状態は放置しない
- **先行設計（まだ実装していない仕様）**: 大きな機能や枠組みを先にdocsで設計する
  ことは正当な作業であり、むしろ推奨される。この場合「実ファイルと一致しない」
  のは異常ではなく想定通りの状態。ただし**それが先行設計であることが分かるように
  明示しなければならない**（下記「実装状況の明示」）

問題なのは、どちらの状態かが分からないまま放置され、「これは未実装なのか、
それとも実装したのにdocsを更新し忘れただけなのか」が判別できなくなること。

## 実装状況の明示

先行設計を含むdocsファイル・節には、冒頭か該当箇所に実装状況を明記する。

```markdown
> **実装状況: 未実装**（Issue #42 で対応予定）
```

```markdown
> **実装状況: 一部実装**（◯◯までは実装済み、△△は未実装）
```

状態は3種類:
- `実装済み` — 明記しなくてよい（デフォルトの想定）
- `未実装` — 先行設計。対応するIssue番号があれば書く
- `一部実装` — 何が実装済みで何が未実装かを一言添える

機能を実装したら、対応するdocsの実装状況マーカーを更新する（`未実装`→記載を削除、
または`実装済み`に変更）のを、その実装のPRに含める。マーカーの更新漏れが一番多い
ズレの原因になるので、実装のPRを出す前に必ず確認する。

## 対応表（何を変えたら何を直すか）

すべてのdocsを同じ強さで扱うと、些細な設定変更のたびにチェックコストが発生し
「軽いフローにしたい」という前提と噛み合わない。そのため2段階に分けている。

**厳格（同一PR内で必ず更新。実装済み内容とのズレを残さない）**

| 実ファイルを変更したら | 同じPR内で更新するdocs |
|---|---|
| `supabase/migrations/`（DBスキーマ） | `docs/architecture.md`（該当テーブルの定義） |
| テストの粒度・実行方法を変えた（例: E2Eの対象追加） | `docs/testing-strategy.md` |
| ブランチ保護設定・Vercel設定・`ci.yml`のトリガー | `docs/git-workflow.md` |
| 実装する/しない機能の方針を変えた | `docs/scope.md` |

**緩め（気づいたタイミングで直せばよい。リリースをブロックしない）**

| 実ファイルを変更したら | 更新するdocs |
|---|---|
| `.github/workflows/`配下の細かい実装（steps、job名など） | `docs/config-templates.md` |
| `.github/ISSUE_TEMPLATE/*` / `pull_request_template.md`の文言レベルの調整 | `docs/config-templates.md` |

「厳格」に分類したものは、動作や設計判断そのものに関わり、ズレると実装ミスや
運用事故に直結する。「緩め」は運用メモに近く、多少古くても実害が小さいため、
毎回のPRで律速要因にはしない。

逆方向も同じ強さで守る: `docs/`側を変更した場合、それが実ファイルの変更を伴う
決定であれば、同じPR内で実ファイルも変更する（「決めた」だけでdocsに書いて
実装を後回しにする場合は、必ず「実装状況の明示」に従って`未実装`マーカーを付ける。
マーカーなしで「決めただけ」の状態を残さない）。

## 作業前後のチェック

- **作業前**: 関連する`docs/`を読んだら、実ファイル（コード・設定・migrations）を
  実際に見て、記述と食い違っていないか確認する。古いdocsの記述をそのまま信じて
  実装しない
- **作業後（PRを出す前）**: 上の対応表を見て、変更した実ファイルに対応する
  docsがあれば更新されているか確認する

## ズレを見つけた時の対応

docsと実ファイルの内容が食い違っていることに気づいたら、まず**実装状況マーカーの
有無を確認する**。

1. `未実装`/`一部実装`マーカーがある → 想定通りの先行設計。実装作業のタスクとして
   扱えばよく、「ズレ」として報告する必要はない
2. マーカーがない（＝実装済みのはずの内容）のに実ファイルと食い違っている：
   - 些細な表現のズレ（誤字、順序程度）→ その場で直してよい
   - 設計判断に関わるズレ（例: docsには「RLSはorganization単位のみ」とあるのに
     実装はrole別の細かい制御までRLSでやっている）→ 自己判断で書き換えず、
     どちらが正しい状態か人間に確認してから進める。曖昧なまま両方が存在する
     状態でPRを出さない

判断に迷った場合（先行設計なのか、更新し忘れなのか自信が持てない場合）は、
1として扱って作業を進めるのではなく、人間に確認する。
