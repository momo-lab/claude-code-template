# テスト戦略

**読むタイミング**: テストコードを書く/変更する時。

## 方針

関数単位のユニットテストを網羅的に書くと、リファクタのたびにテストを大量に書き直すことになり
開発速度が落ちる。そのため **統合テストを主力** に据え、ユニットテストは
「DBに依存しない、かつ複雑なロジックのみ」に絞る。

テストは「内部でどの関数を呼んだか」ではなく「入力 → DBの状態 → 出力」という振る舞いを
検証する。これにより、内部実装をリファクタしてもテストが壊れにくくなる。

## レイヤー別方針

### 1. ユニットテスト（最小限・Vitest）

対象は次のような **DBに依存しない純粋関数** のみ:
- 複雑な計算・判定ロジック（料金計算、日時の重複判定、権限マッピングの解決など）
- 外部I/Oを持たないバリデーションロジック

DBアクセスを含む関数、Server Action、API Routeはユニットテストの対象にしない
（→ 統合テストで検証する）。

### 2. 統合テスト（主力）

**ローカルSupabase (`supabase start` で起動するDocker上のPostgreSQL) を実DBとして使う。**
モックやin-memory DBは使わない（RLSの検証にはPostgreSQLの実挙動が必須なため）。

粒度は Server Action / API Route 単位。「主要なユースケース1つ = 統合テスト1つ」を目安にする。

**マルチテナント/権限分離のロジックがある場合は、専用のテストスイートを必ず用意する。**
「テナントAの権限でテナントBのデータを読み書きできないこと」のように、ビジネス上
クリティカルな保証は、他のテストと同じ粒度で終わらせず意図的に手厚くする。

セットアップ/クリーンアップ:
- テスト実行前にseedスクリプト（`supabase/seed.sql`など）ベースの既知データを投入
- 各テストはトランザクション内で実行しロールバックする（またはテスト後にtruncate）
  ことで、テスト間の状態汚染を防ぐ
- 実行順に依存するテストを書かない

**注意（Vitestのファイル並列実行）**: 単一の共有ローカルDBに対してtruncate
ベースでリセットする上記の方式は、Vitestのデフォルトのファイル並列実行と
相性が悪い。複数のテストファイルが並列実行されると、あるファイルの`truncate`が
別のファイルが実行中のデータを消してしまい、外部キー制約違反などで間欠的に
失敗する（再現性が低く原因調査に時間がかかりやすい）。統合テスト用のVitest設定
では`fileParallelism: false`を設定し、テストファイルを直列実行すること。

```ts
// vitest.integration.config.ts
export default defineConfig({
  test: {
    fileParallelism: false, // 共有DBをtruncateでリセットするため直列実行必須
    // ...
  },
});
```

### 3. E2E（少数精鋭・Playwright）

ブラウザを実際に操作して確認する価値がある、コアなユーザージャーニーのみを数本。
実行コストが高いため、全PRでは回さず **develop→mainのリリースPR時のみ** 実行する
（`docs/git-workflow.md`のリリースフロー、`.github/workflows/ci.yml`と対応）。

## テストを書く順序（TDDのサイクル）

1. 統合テストで「入力 → 期待するDB状態/レスポンス」を先に書く（失敗する状態）
2. Server Action / API Routeを実装してテストを通す
3. 複雑な計算ロジックが出てきたら、その部分だけ純粋関数に切り出してユニットテストを足す
4. リファクタ時は統合テストの粒度（振る舞い）を変えずに内部実装だけ変更する

## プロジェクトごとに埋めるべきこと

- [ ] このプロジェクトで「専用の手厚いテストスイート」が必要な、クリティカルな
      分離/権限ロジックは何か（例: マルチテナント分離、決済関連の整合性など）
- [ ] E2Eでカバーする「コアなユーザージャーニー」の一覧
- [ ] MVPフェーズでテストしないと決めた範囲（`docs/scope.md`と対応させる）
